# Clinical interface

TASK-CON-03 provides the consultation editor at `/clinical`: patient-scoped history, versioned draft save, explicit sign confirmation, read-only signed original and ordered dated corrections. The page is clinician-role gated by the shared staff session UI. Backend role and patient-record checks remain authoritative.

The patient and consultation screens follow the Member B Living Heritage frames supplied on 4 November 2026. The wider left card holds the draft or signed original; the right card holds guidance or history. The dated correction form opens from the header action. The care-plan view places the ordered pathway to the left of current decision controls, with the project paper, forest, botanical and brass assets. Real UUID handoff, required checkboxes and recorded clinical reasons remain because the backend contract needs them. See [visual comparison](../../../../docs/evidence/member-b-figma-alignment-2026-11-04.md).

The client API calls in `api.ts` follow B's contract in `docs/api/member-b-contract.md`. With authentication explicitly configured, the Go API registers protected consultation routes and enforces active clinician role plus patient assignment. Administrators grant or revoke assignments at `/administration/clinical-assignments`; their role alone never grants clinical-note access. The signed clinic source and integrated AT03 journey remain review gates. Do not publish these routes in OpenAPI until endpoint review is recorded.

`/clinical/plans` shows the assigned clinician the fixed pathway, explicit draft-to-preparatory start action, stage checklist, version, hold/resume/cancel reason form and dated decision history. It calls the protected B plan API. A 409 on advancement or cancellation means required scheduling/preparation integration evidence is unavailable; the screen must not imply the plan changed. The backend remains the authority for record access and stage prerequisites.

Hold and cancellation now require an explicit confirmation after the clinician enters a reason. A conflicting or inaccessible mutation clears the selected plan so stale action buttons cannot be reused; the clinician can select the plan again to reload it. The clinical page uses the shared Living Heritage palette and keeps decision outcomes in an announced status or alert.

`/clinical/preview` is available only in Next.js development mode. It uses synthetic consultation records and browser memory for its actions; it makes no clinical API or database writes. It is for screen review, not AT03 evidence. Signing fields, correction reason rules and record access still require clinic/team review. No real patient data belongs in the preview.
