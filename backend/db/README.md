# Database foundation

Run `go run ./cmd/migrate` from `backend/` with `DATABASE_URL` set. Forward migrations are embedded in the executable, applied in filename order, recorded in `schema_migrations`, and protected by a transaction-level advisory lock. The pending batch runs in one transaction. Run migrations explicitly before starting the API.

Use six-digit sequential filenames. `000001`–`000005` are allocated to identity, roles, throttling, audit integrity, billing and patients. Both audit and billing landed with prefix `000004`; the runner keys applied versions by complete filename, so retain these already-merged names. The next available number is `000006`; recheck the latest `dev` before assigning it. Coordinate numbers across owners and never edit/rename an applied migration. Review backup/restore before destructive changes; there is deliberately no automatic down migration.

The schema contains identity, role, server-session, throttle and audit storage. Optional session behavior and the transactional audit writer are implemented; audit UPDATE/DELETE/TRUNCATE operations are rejected by database triggers. The audit reader requires an explicit authorization adapter; AUTH-03 still supplies shared role/record protection. No credentials are seeded automatically; `cmd/seedstaff` requires explicit synthetic development input. `btree_gist` is enabled for future scheduling exclusion constraints.

The billing schema exists; its permissions still await AUTH-03. The patient schema is drafted in `000005_patients.up.sql` under provisional DEC02 rules; A must confirm its number before integration and C must review its fields/identity constraint. Billing currently has an unconstrained `invoices.patient_id`; E/A must add its patient foreign key in a new follow-up migration after the patient table is integrated. Clinical, scheduling and stock schemas remain pending agreed field rules. Use `timestamptz` for event times, PostgreSQL `date` for expiry, integer minor units for LKR, and `numeric` with an agreed decimal scale for grams. Enforce half-open booking intervals and uniqueness for retries in their module migrations. Every new migration is applied by the generic PostgreSQL fixture and fresh/repeat migration tests in CI.
