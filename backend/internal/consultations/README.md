# Consultation drafts (TASK-CON-01)

Member B owns this slice; Member C reviews it. SRS CON-01 and AT03 require a consultation draft to exist without a care plan. Migration `000006_consultation_drafts.up.sql` creates draft-only rows linked to patients and staff, with a version for concurrent edits. `Create`, `Get`, and `Update` preserve Unicode note text, reject blank/oversized drafts, lock and version edits, and insert create/update audit metadata in the same transaction. Audit events contain no note body.

Every service call requires a transaction-scoped `AccessPolicy`. A nil policy denies access. The production clinician-to-patient assignment source remains open under DEC02, so no clinical HTTP route is registered. CON-03 adds a client screen against the proposed contract, but live calls cannot reach these services until protected HTTP integration is reviewed. A future policy must verify the active clinician role and current patient/consultation assignment in the same transaction, including owner-versus-assigned draft rules, before A's session/CSRF middleware may expose routes. The test policy is synthetic and grants no production access.

TASK-CON-02 adds migration `000007_consultation_signing.up.sql` (number pending A confirmation). A versioned `Sign` moves the draft into a separate `signed_text` column and stores server-derived signer and time. Signed consultations cannot be updated or deleted, including through direct SQL; addenda are separate insert-only rows ordered by recorded time and ID. `AddCorrection` requires a nonblank reason and body, and writes audit metadata in the same transaction. `Get` returns the signed original and dated addenda only after the same transaction-scoped record-access check. `CanEdit` also gates signing and adding corrections; the future production adapter must apply the approved clinician assignment and action rules to those operations. No text or correction reason enters audit events.

The previous draft-only migration remains untouched. The provisional reason limit is 2,048 UTF-8 bytes and the body limit is 65,536 bytes; clinic signing fields and reason policy still require DEC02. CON-01 follow-up branch `member-b/con-01-clinical-access` adds a proposed `000008` patient/clinician assignment table, a transaction-scoped active-role and active-assignment policy, a bounded text-free history summary, and protected draft create/list/detail/update handlers for integration tests. CON-02 follow-up branch `member-b/con-02-signing-http` adds protected `POST /consultations/:id/sign` and `POST /consultations/:id/addenda` handlers with server-derived actor/time, strict requests, assignment checks and session/CSRF enforcement in integration tests. The assignment grant/revoke authority remains undecided, so the application does not register these clinical handlers in `cmd/api` yet. A/C must review the allocation and access contract before live registration. CON-03 owns the editor and history screen. OpenAPI stays unchanged until endpoints are implemented and reviewed. PostgreSQL tests cover draft-without-plan, sign/edit races, immutable history, denied access and audit rollback; these are implementation evidence, not AT03 acceptance.
