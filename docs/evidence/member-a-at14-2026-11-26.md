# AT14 isolated performance baseline

The baseline covers TASK-QA-05, which F owns with A responsible for host support and review. Its acceptance target is valid patient search, availability and invoice retrieval responses with p95 below 2,000 ms for each operation. Five simulated staff run for ten minutes with 500 patients, 1,000 therapy sessions and 200 stock batches.

## Setup and workload

The [AT14 workflow](../../.github/workflows/at14-performance.yml) uses a disposable GitHub Actions runner and an empty local PostgreSQL 17.11 database. It migrates the schema, creates synthetic staff and seeds the exact dataset plus 500 issued invoices with one line each. It builds Next.js and runs the real Go API behind the Next.js rewrite and a loopback HTTPS proxy. The launcher requires a loopback database named `ayurflow_auth_e2e` and checks it is empty before applying migrations.

After checking all three responses, two receptionists search for different patients, one therapist reads room and therapist availability, and two billing staff retrieve issued invoices. Each has a separate signed-in session and starts approximately one request per second, waiting for any slow request to finish before sending another. Requests are timed through response validation. The result includes the per-operation request count, p95 using nearest rank, and error counts. A test passes when all operations have zero errors and p95 below 2,000 ms. Only aggregate measurements are uploaded.

To repeat the isolated baseline, follow the [disposable full-stack setup](../../frontend/tests/fullstack/README.md) through the build, then run `npx playwright test --config playwright.performance.config.ts` from `frontend`. The performance config uses 15-minute idle and 20-minute absolute timeouts for this fixture. Chromium is unnecessary for these API measurements. The shared browser suite keeps its short expiry settings.
